## 과제 목표
이번 과제를 통해 무엇을 배우고자 했는지 간단하게 작성해요.

- React(Vite) 기반 로컬 스토리지 Todo 앱을 Next.js 15 App Router 구조로 성공적으로 마이그레이션하며 파일 기반 라우팅의 동작 방식을 이해했습니다.
- Server Component와 Client Component의 차이를 이해하고, 사용자 상호작용이 필요한 부분(`"use client"`)과 데이터를 패칭하는 부분을 명확히 분리하여 적용했습니다.
- FastAPI를 활용해 Todo CRUD API를 직접 구현하고, Next.js의 `actions.ts` 및 `route.ts`와 연동하는 풀스택 데이터 흐름을 경험했습니다.
- 메인 스레드를 블로킹하는 로컬 스토리지 상태 관리에서 서버 API 기반 데이터 비동기 처리로 전환하며 성능 및 아키텍처의 차이를 이해했습니다.

## AI 활용 내역
AI를 활용해 구현하거나 수정한 내용을 기록해요.
단순히 어떤 프롬프트를 썼는지보다, 어떤 결과를 받았고 어떻게 수정했는지를 중심으로 작성해요.

### Next.js 및 FastAPI 기본 세팅 및 통신 연동
- AI 활용 내용 : 
가장 먼저 "Next.js App Router 구조와 FastAPI로 기존 과제를 마이그레이션해줘"라고 프롬프트를 작성해 기본 세팅과 구조에 대한 계획(implementation_plan)을 받았어요. 클라이언트 요청이 `route.ts` 프록시를 거치거나 `actions.ts`를 통해 백엔드 `main.py`의 엔드포인트와 통신하는 뼈대 코드를 얻을 수 있었습니다.
- 직접 수정한 부분 : 
`package.json`이나 `requirements.txt`에 누락된 패키지가 없는지 확인하고, `fetch` 함수 옵션에서 `cache: 'no-store'`를 적용하여 항상 최신 데이터를 받아오도록 직접 옵션을 수정했어요.
- 수정 이유 : 
Next.js의 기본 캐싱 정책 때문에 백엔드에서 Todo를 추가하거나 지워도 프론트엔드 화면에 바로 반영되지 않는 문제가 발생하여, 매번 신선한 데이터를 패칭해야 한다고 판단했기 때문입니다.

### React Key Prop 에러 및 타임존 처리 문제 해결
- AI 활용 내용 :
화면에 리스트를 렌더링할 때 콘솔창에 경고가 뜨고, 자정 무렵에 Todo를 추가하면 다음 날짜로 넘어가는 현상(타임존 밀림)에 대해 "React에서 key prop 경고가 뜨는 이유와, 해외 타임존에서 날짜가 밀리는 현상을 어떻게 처리해야 해?"라고 질문하여 해결 코드를 받았습니다.
- 직접 수정한 부분 :
받은 답변을 토대로 백엔드의 `datetime` 객체를 `timezone.utc` 기반으로 모두 변경하고, `TodoList.tsx`의 `.map()` 부분에 `key={todo.id}`를 명시적으로 삽입했습니다. 
- 수정 이유 :
프론트엔드에서 고유 key가 없으면 상태 꼬임 버그가 생기며, 시간 처리를 클라이언트 로컬 기준이 아닌 서버(UTC) 기준으로 통일해야 글로벌 서비스 환경이나 서머타임(DST) 적용 지역에서도 오류가 없기 때문입니다.

## 구현하면서 고민한 점
구현 과정에서 막혔던 부분이나 고민했던 내용, 해결 방법을 자유롭게 작성해요.

- 고민한 점 : "거대해진 App.jsx를 어떻게 분리할 것인가?", 그리고 "어디까지 서버 컴포넌트로 만들고 어디부터 클라이언트 컴포넌트로 만들 것인가?"가 가장 큰 고민이었습니다.
- 해결 방법 : 데이터 패칭이 일어나는 가장 상단의 `page.tsx`는 서버 컴포넌트로 두고, 사용자 클릭(이벤트 리스너)이나 상태(state) 변경이 일어나는 폼 입력창, 토글 버튼, 리스트 컴포넌트 등은 제일 상단에 `'use client'`를 선언하여 잘게 쪼갰습니다. 이 과정에서 `initialTodos`를 props로 넘겨주는 패턴을 활용했습니다.

## 과제 회고
과제를 마치고 느낀 점, 아쉬운 점, 다음에 개선하고 싶은 점을 자유롭게 작성해요.

- 잘한 점 : 로컬 스토리지에만 의존하던 프론트엔드 코드에서 벗어나, 직접 백엔드 API를 만들고 연동해 보며 '풀스택'의 데이터 흐름을 이해한 점이 뿌듯합니다. 검색 폼에 디바운스(Debounce)를 적용해 불필요한 API 호출을 줄인 것도 좋은 최적화 경험이었습니다.
- 아쉬운 점 : 서버 컴포넌트와 클라이언트 컴포넌트 간의 경계가 아직 완전히 익숙하지 않아 컴포넌트를 설계할 때 헷갈리는 부분이 있었습니다.
- 다음에 시도해볼 것 : Next.js 15의 Server Actions와 `useOptimistic` 훅을 더 깊이 공부해, 로딩 지연 없이 사용자가 버튼을 누르자마자 UI가 즉각적으로 반응하는(Optimistic Update) 고도화된 UI를 구현해보고 싶습니다.
